# 5. A song module decodes once and owns the time base

Status: accepted

## Context

The song was decoded once for analysis in the ViewModel and again by the exporter. The waveform
was computed in the ViewModel and duplicated in the screenshot test. Frame ↔ time conversion was
two free functions that disagreed with each other: `msToFrame(frameToMs(f))` returned `f - 1` for
most frames because both rounded down, so seeking to a frame landed one frame early. After the
song ended the playhead could stop short of the last frame, and pressing play again resumed at
the end and finished immediately instead of rewinding.

## Decision

- **`audio/Song`** holds the decoded PCM, the frame count, the waveform and the analysis.
  `Song.decode(file, frames)` is the Android entry point; `Song.of(pcm, frames)` is pure and is
  what the tests and the screenshot test use. Export transcodes `song.pcm` instead of decoding
  the file again.
- **`audio/Timebase`** is the one frame ↔ millisecond mapping: a frame starts at
  `ceil(f * 1000 / 60)` ms, `frameAt(ms)` is `floor(ms * 60 / 1000)`, so the round trip is exact.
- Reaching the end of the song parks the playhead on the last frame, and play from the last
  frame rewinds to 0.

## Consequences

The Composer timeline dots now use the first whole millisecond of a frame (frame 1 is 17 ms,
was 16 ms). The screenshot test's waveform is the real one, normalised to the loudest frame, so
its band is slightly taller than the old copy drew it.

## Alternatives considered

- **Keep only the mono analysis copy and re-decode for export.** Saves memory during editing
  (about 10 MB per minute of stereo audio) at the cost of a second decode on every export.
  Decoding once was the requested behaviour; revisit if long songs cause memory pressure.
- **Store time in microseconds everywhere.** Exact, but every UI and file format value is in
  frames or milliseconds already.
